# gRPC between Order and Inventory: Four Call Types and Retries

## Context
Group assignment:
- implement communication between the project's services with gRPC on Spring Boot 4.1 and Java 25;
- describe the contract in a `.proto` file and implement all four call types: unary, server streaming, client streaming and bidirectional streaming;
- configure retries for gRPC calls when a service is temporarily unavailable;
- test the methods and that retries fire on failures or a temporarily unavailable server.

The report shows the retry configuration, logs of the requests and the recorded retries.

*References:* [Order spec](../../design/services-specs/order-service-spec.md), [Inventory spec](../../design/services-specs/inventory-service-spec.md), [Order task 05 (resilience)](../order-service/), `order-service/.../ports/StockReservations.java`

## Decisions (2026-11-05)
1. **Order (client) → Inventory (server).** Checkout depends on this link, so retries matter there.
2. **The four call types, each used by a real Order flow** (service `voltstore.inventory.v1.StockService`):

   | Type | Method | Used by |
   |---|---|---|
   | Unary | `ReleaseReservation` | the cancellation saga and the clean-up after a failed placement |
   | Client streaming | `ReserveStock` | checkout: Order streams the order's items; Inventory reserves all or nothing when the stream completes and answers once |
   | Server streaming | `GetStockLevels` | `POST /orders/validate`: available quantities of the cart's products |
   | Bidirectional | `ReleaseReservations` | the payment-window expiry job and the orphan-reservation job: up to 100 releases on one stream, a result per order as each is done |

3. `POST /orders/validate` also compares the cart with Inventory's quantities and reports `INSUFFICIENT_STOCK` (a reason that already exists) when a quantity exceeds what is available. The OpenAPI document and the spec are updated.
4. Inventory keeps its HTTP reservation endpoints (EP-INV-06/07: in the spec, handy for tests). Order's HTTP adapter for Inventory is replaced by the gRPC one; gRPC is Order's only way to Inventory's reservations.
5. The contract `inventory_stock.proto` lives in Inventory. Order keeps a copy (each service builds on its own; the Docker build context is the service folder), and a test in Order fails when the two copies differ.
6. **Retries:**
   - the channel's gRPC `retryPolicy`: 4 attempts, back-off 0.3 s → 0.6 s → 1.2 s (capped at 2 s), only for status `UNAVAILABLE`;
   - Order's Resilience4j retry for Inventory is removed so retries do not multiply; the circuit breaker stays;
   - both operations are idempotent (reserve by `orderId`, release always);
   - a client interceptor logs every attempt with its number (gRPC's `grpc-previous-rpc-attempts` header).
7. **Infrastructure:**
   - Inventory serves gRPC on port **9090**, next to HTTP 8080;
   - the port is added to Compose, the Kubernetes Service and the NetworkPolicy (only Order may reach it);
   - the internal token travels as gRPC metadata `x-internal-token`, checked by a server interceptor like the HTTP filter;
   - tracing continues through gRPC (Spring gRPC observations).
8. **Tests:**
   - integration tests of the four methods against a real server;
   - a retry test (`UNAVAILABLE` twice, then success: attempts counted, the call succeeds);
   - a "server down, then up" test;
   - "four failures" ends as 503 in Order;
   - a run on minikube with Inventory stopped and started again, the retries visible in the logs.
9. Branch `infrastructure/grpc-order-inventory` from `main`, one PR; cross-service work agreed (Order, Inventory, Compose, `k8s/`).
10. Documents in English: this task, the report `docs/reports/grpc.md`, and the Order and Inventory specs synced at the end.

Details decided while planning (inside the decisions above):
- `GetStockLevels` is a soft check, like the Catalog part of `/orders/validate`. If Inventory cannot answer, validation goes on with Catalog's result alone (the reservation at submission decides anyway), and a warning is logged.
- The gRPC deadline of each call is 3 s, the former HTTP read timeout to Inventory, and covers all attempts (see Deviations).
- The protobuf code is generated by `io.github.ascopes:protobuf-maven-plugin`, preconfigured by `spring-boot-starter-parent` 4.1.2 (protoc 4.36.2, grpc-java 1.84.1).

## Implementation Notes (2026-11-05)
- **Contract:** `inventory-service/src/main/protobuf/inventory_stock.proto`; Order's copy is `order-service/src/main/protobuf/inventory_stock.proto`. Both services declare `io.github.ascopes:protobuf-maven-plugin` (configured by the parent) plus `grpc-protobuf` and `grpc-stub`.
- **Inventory:**
  - `grpc/StockGrpcService` (`@GrpcService`) implements the four methods over `ReservationService` and the new `StockService.availableQuantities`;
  - `grpc/GrpcConfig` holds the token interceptor (`@GlobalServerInterceptor`, constant-time compare) and the `GrpcExceptionHandler`;
  - `grpc/GrpcErrors` maps errors: transient data-access failures → `UNAVAILABLE`, the rest → `INTERNAL`;
  - the server listens on `${GRPC_PORT:9090}`; tests use port 0 and the in-process transport.
- **Order:**
  - `clients/InventoryGrpcAdapter` implements `StockReservations` (now with `releaseAll`) and the new port `StockLevels`;
  - `clients/InventoryGrpcConfiguration` creates the channel (`GrpcChannelFactory`, name `inventory`), the stubs, the token metadata and `AttemptLogging` (a `ClientStreamTracer` per attempt, so retries are logged);
  - the jobs call `releaseAll` once per run;
  - `CheckoutCheckService` adds Inventory's quantities;
  - `InventoryClientAdapter`, the Inventory HTTP client and `clients.inventory` are gone, and the Resilience4j retry instance for Inventory too; the circuit breaker records `StatusRuntimeException`.
- **Configuration:**
  - Order: `spring.grpc.client.channel.inventory` (target, `default.deadline`, `service-config.method[].retry`); env `INVENTORY_GRPC_TARGET`, `INVENTORY_DEADLINE`.
  - Compose maps 9090; the Kubernetes Service and Deployment have a `grpc` port; Order's ConfigMap sets the target; NetworkPolicy `inventory-grpc-from-order-service`.
  - Order's `openapi/public.json` was regenerated (the validate description), and so was the frontend's generated `order.ts`.
- **Tests:**
  - Order uses `support/FakeInventory`, a scriptable StockService on a local port (failures for N attempts, answers, delays, call log) in place of WireMock for Inventory, in `InventoryGrpcAdapterTest`, `InventoryGrpcConnectionTest` and the Checkout, Cancellation and Fulfillment/Expiry integration tests;
  - `InventoryProtoCopyTest` compares the two contracts;
  - Inventory has `StockGrpcServiceIntegrationTest`.
- **Verified:**
  - Order 386 tests and Inventory 404 tests, all green;
  - on minikube: checkout over gRPC, Inventory scaled to 0 (4 attempts per call in Order's log, `503` for the checkout, `204` for the cart check), then the orphan job releasing on the bidirectional stream once Inventory was back;
  - report: `docs/reports/grpc.md` with `grpc/test-retries.log` and `grpc/minikube-retries.log`.

## Deviations from spec / task
- **The deadline comes from a new property, `INVENTORY_DEADLINE`**, not from `clients.inventory.read-timeout` as planned. That property belonged to the removed HTTP client. The default is the same 3 s.
- **Order's tests run the fake Inventory on a real local port, not in-process.**
  - With `grpc-inprocess` on the classpath, Spring gRPC's in-process channel factory takes over named channels and refuses the target `inventory`.
  - The real port also exercises the transport used in production, which the connection-refused test needs.
  - Inventory's own test uses the in-process transport; Order's tests set `spring.grpc.client.inprocess.enabled=false`.
- **One test overrides the back-off.** The "Inventory comes up late" test uses longer waits than production (up to 1/2/4/4 s), because the channel's own reconnect pause (about 1 s) could otherwise use up all four production attempts. The test explains it, and so does the report §4.
- **Found and fixed in passing:** moving the orphan job to batches first lost its per-attempt `try/catch` around the "does the order exist" check. A test (`oneFailingAttempt_doesNotStopTheRun`) caught it, and the check is guarded again.

## Technical Notes / Constraints
- gRPC retries apply only before the client has received response headers or messages; a streaming call that has already received data is not retried. The client buffers the messages it has sent so it can replay them (limit `perRpcBufferLimit`, 1 MiB by default, far above 100 items).
- `UNAVAILABLE` is the status of a refused or reset connection and of a server shutting down; `DEADLINE_EXCEEDED` is not retried, because the deadline already covers every attempt.
