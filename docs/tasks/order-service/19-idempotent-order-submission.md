# EP-ORD-02: Idempotency-Key on Submit Order

## Context
A repeated "Submit order" (double click, a retry after a lost answer, two tabs) creates a second order with its own reservation today; the unpaid one holds stock until it expires. `POST /orders` gets an optional `Idempotency-Key` header so a repeat with the same key and body returns the first order and reserves nothing (frontend backlog [BL-07](../../../frontend/docs/backlog/BL-07-order-submit-idempotency.md), agreed 2026-10-22). The cleanup of old and stranded keys is [task 20](20-purge-idempotency-keys-job.md), which builds on this one; this task works without it.
*References:* [Order Spec — EP-ORD-02 (*Idempotency-Key*), Responses and errors, Decisions D4–D10](../../design/services-specs/order-service-spec.md), [API Contracts — `POST /orders`](../../design/services-requirements/api-contracts.md), [OpenAPI Conventions — D5, D6](../../design/services-requirements/openapi-conventions.md), [task 08 (submit order)](08-submit-order.md), [task 17 (reservation attempts)](17-review-fixes.md)

## Acceptance Criteria
- [x] **Migration `V4__create_idempotency_keys_table.sql`:** `idempotency_keys (customer_id UUID, idempotency_key UUID, request_hash VARCHAR(64), status VARCHAR(16) CHECK IN ('IN_PROGRESS','COMPLETED'), order_id UUID NULL, created_at TIMESTAMPTZ)`, primary key `(customer_id, idempotency_key)`, a check that `order_id` is set exactly when `status = 'COMPLETED'`, an index on `(status, created_at)` for task 20. A header comment in the style of `V3` explains what a row means.
- [x] **Header:** `POST /orders` reads the optional `Idempotency-Key`. A non-UUID value → `400` type `validation` (the framework's type-mismatch answer, shaped by `handleExceptionInternal` like a non-UUID path variable; no `errors` map needed). Without the header nothing changes: every existing test passes unchanged.
- [x] **Order of checks:** role check, body validation (`400`), the `X-User-Email` check (`401`), then the claim. A malformed request leaves no row.
- [x] **Claim:** the hash of D9 is computed and the row inserted as `IN_PROGRESS` in its own transaction with `INSERT … ON CONFLICT (customer_id, idempotency_key) DO NOTHING`, before the Catalog call.
- [x] **Existing row:** nothing is called and nothing is reserved. Different hash → `422` type `idempotency-key-mismatch` (whatever the status). `COMPLETED` → `201` with the body built from the order's current state (`PlacedOrderResponse.of(order)`), `Location: /orders/{orderId}` and `Idempotent-Replayed: true`. `IN_PROGRESS` → `409` type `request-in-progress` with `Retry-After: 1`.
- [x] **Complete:** the row becomes `COMPLETED` with `order_id` inside the transaction that stores the order, writes `OrderPlaced` and deletes the reservation attempt. If the row is missing, the order is still stored and a warning is logged.
- [x] **Release on failure:** every non-`201` outcome after the claim (`IneligibleItems`, `OrderTotalTooLarge`, `InsufficientStock`, `DependencyUnavailable`, a failed save) deletes the row in its own transaction, best-effort with a warning log; the original exception is still thrown. The reservation-attempt handling of steps 4–6 is unchanged.
- [x] **Unit tests** (`RequestHashTest` or similar): the same request with items in another order or other JSON whitespace gives the same hash; a changed quantity, product, or any `deliveryDetails` field gives another hash.
- [x] **Unit tests** (`OrderPlacementServiceTest`): owner path claims then completes; a replay of a `COMPLETED` key makes no Catalog or Inventory call; mismatch and in-progress answers; each failure type deletes the claim; no header → no row touched.
- [x] **Controller tests** (`OrderControllerTest`): non-UUID key → `400`; replay → `201` with `Location` and `Idempotent-Replayed: true`; `422 idempotency-key-mismatch`; `409 request-in-progress` with `Retry-After: 1`; the problem `type` URIs.
- [x] **Integration tests** (`CheckoutIntegrationTest`, Testcontainers PostgreSQL + WireMock):
  - two sequential requests with the same key and body → one order, one `POST /inventory/reservations` and one Catalog call, both answers carry the same `orderId`, the second with `Idempotent-Replayed: true`;
  - **two concurrent requests** with the same key (WireMock delays the Inventory answer) → one order and one reservation call; the other answer is `409 request-in-progress` or the replayed `201`;
  - same key, another body → `422`, one order only;
  - Inventory answers `503` first, then `204`: the retry with the same key creates the order (the claim was released);
  - the same key from two customers → two orders;
  - a replay after the order was paid shows `status: PAID`.
- [x] **OpenAPI:** the header parameter `Idempotency-Key` (`in: header`, `format: uuid`, not required) on `POST /orders`; the `201` documents the response header `Idempotent-Replayed`; `409` (`Problem`) added; the `422` `oneOf` gets `Problem` for `idempotency-key-mismatch`. `order-service/openapi/public.json` regenerated with `-Dopenapi.update=true` and committed.
- [x] **Through the gateway (manual, Compose):** two `POST http://localhost:8080/orders` calls with a customer token and the same `Idempotency-Key` return the same `orderId`; the second has `Idempotent-Replayed: true`. Both requests are added to the Order folder of `VoltStore_API_Tests.json`.
- [x] All Order tests pass (`mvnw.cmd verify` in `order-service/`).

## Technical Notes / Constraints
- **Settled decisions (D4–D10), do not change:** a separate table with an `IN_PROGRESS` claim (not a column on `orders`, not an `orderId` derived from the key); optional header, UUID only, scoped per customer; only success is remembered; the replay is built from the current order, not a stored body; `422` mismatch before status, `409` in progress with `Retry-After: 1`; the hash of D9; cleanup only in task 20.
- **Hash (D9):** SHA-256 hex of the parsed `PlaceOrderRequest` serialised by the application's Jackson `JsonMapper` with `items` sorted by `productId`. Record components serialise in declaration order, so the JSON is stable; do not hash the raw request bytes.
- **Claim insert:** a native `@Modifying` query returning the row count (`1` = owner, `0` = existing row), then a plain `findById` for the existing row. A `save()` of a new entity followed by catching `DataIntegrityViolationException` is not enough: the violation surfaces at flush and poisons the transaction.
- **No transaction during remote calls** stays true: claim, release and the replay lookup are each their own short transaction; only completion joins the step-5 transaction.
- Problem types go through `GlobalExceptionHandler.problem(...)` like the others (new exceptions, e.g. `IdempotencyKeyMismatchException`, `RequestInProgressException`); `Retry-After` is set the way the `503` handler sets it.
- The header is read in `OrderController.place` with `@RequestHeader(name = "Idempotency-Key", required = false) UUID`; Spring's conversion failure already reaches `GlobalExceptionHandler.handleExceptionInternal`, which gives it the `validation` type and the shared fields. Verify with the controller test rather than adding a handler.
- Generated frontend types change with `public.json`; the frontend adapts on its side (its `check:api`), nothing in `frontend/` is edited here.
- The gateway needs no change: it strips only `Authorization`, `X-User-*` and `X-Internal-Token`.

## Implementation Notes (2026-10-22)
- **Schema:** `V4__create_idempotency_keys_table.sql` as specified: primary key `(customer_id, idempotency_key)`, a `CHECK` on the two statuses, `chk_idempotency_keys_order` (`order_id` set exactly when `COMPLETED`), and `idx_idempotency_keys_status_created` for task 20. `IdempotencyKey` maps it with an `@EmbeddedId` record (`IdempotencyKey.Id`) and is only read through JPA.
- **`IdempotencyKeyRepository`:** three native `@Modifying` statements, each returning a row count: `claim` (`INSERT … ON CONFLICT (customer_id, idempotency_key) DO NOTHING`, `1` = owner), `complete` (`UPDATE … SET status = 'COMPLETED', order_id` where the row is still `IN_PROGRESS`) and `release` (`DELETE` where still `IN_PROGRESS`).
- **`services/IdempotencyKeys`** wraps them. `claim` computes the D9 hash, runs the insert in its own transaction, and when the row existed reads it in a second short transaction: another hash → `IdempotencyKeyMismatchException`, `IN_PROGRESS` → `RequestInProgressException`, `COMPLETED` → the order ID to replay. `complete` joins the caller's transaction and logs a warning when no claim is left. `releaseQuietly` runs in its own transaction and only logs a failure. `hash` serialises a copy of the request with `items` sorted by `productId` through the application's `JsonMapper` and returns the SHA-256 hex.
- **`OrderPlacementService`:** new `place(customer, request, idempotencyKey)` returning `Placement(order, replayed)`; the old `place(customer, request)` delegates with `null`. With a key: the email check, then `claim`; a replay loads the order in a short transaction and returns `PlacedOrderResponse.of(order)`; otherwise the existing steps run unchanged, `store` calls `complete` after deleting the reservation attempt, and any `RuntimeException` releases the claim before it is rethrown. The reservation-attempt handling is untouched.
- **`OrderController.place`** reads `@RequestHeader(name = "Idempotency-Key", required = false) UUID` and sets `Idempotent-Replayed: true` on a replay. A non-UUID header is Spring's `MethodArgumentTypeMismatchException`, already shaped by `handleExceptionInternal` (type `validation`, `timestamp`, `service`); no handler was added.
- **`GlobalExceptionHandler`:** `422` type `idempotency-key-mismatch` (title "Idempotency-Key mismatch") and `409` type `request-in-progress` (title "Request in progress") with `Retry-After: 1`, built the same way as the `503`.
- **OpenAPI:** the header parameter (`format: uuid`, not required, with a description), the `Idempotent-Replayed` response header on `201`, a `409 Problem` with `Retry-After`, and `Problem` as the fourth `oneOf` of the `422`. `openapi/public.json` regenerated.
- **API collection:** two requests at the end of the Order folder of `VoltStore_API_Tests.json` ("Submit Order with Idempotency-Key (gateway)", "Repeat Submit Order with the same Idempotency-Key (gateway)") and the collection variables `gatewayUrl`, `customerToken`, `idempotencyKey`. The first generates a key in its pre-request script and stores the `orderId`; the second checks `201`, `Idempotent-Replayed: true` and the same `orderId`.

  - `OrderPlacementServiceTest` (29, 12 new): no key → the key repository is never touched; the owner claims before Catalog and completes after the save; a completion without a claim still stores the order; a replay of a `COMPLETED` key returns the order's current status (`PAID`) with no Catalog, Inventory, attempt or outbox call; a mismatch (even on a `COMPLETED` row) and an `IN_PROGRESS` row answer without calling anyone; `IneligibleItems`, `OrderTotalTooLarge`, `InsufficientStock`, `DependencyUnavailable` and a failed save each release the claim; a failed release does not hide the original exception.
  - `OrderControllerTest` (52, 5 new): the key reaches the service, and `null` without the header; a non-UUID key → `400` type `validation` with `service`, service not called; a replay → `201` with `Location` and `Idempotent-Replayed: true`; `422 idempotency-key-mismatch`; `409 request-in-progress` with `Retry-After: 1` and the detail text. ## Deviations from spec / task
- **`OrderPlacementServiceTest.setUp` changed after all.** The decision was that the service test stays untouched thanks to the two-argument wrapper. The wrapper keeps every existing test method unchanged, but the service's constructor gains `IdempotencyKeys`, so the one constructor call in `setUp` passes it (a real `IdempotencyKeys` over a mocked repository). Alternatives: a second, idempotent placement service wrapping the existing one (rejected: completion must run inside the existing step-5 transaction, so it would need a callback into that transaction); a setter (rejected: no other bean is built that way).
- **Hash code lives in `IdempotencyKeys.hash`, its test is `RequestHashTest`.** The task suggests a separate `RequestHash` class. The hash is used only when claiming, and keeping it next to the claim keeps the D9 rule in one place; the test name follows the task.
- **Row gone between the claim and the lookup → `409 request-in-progress`.** Not covered by the spec: the claim finds a row, but before it is read the first request fails and releases it. Answering `409` with `Retry-After: 1` lets the client's retry claim the key itself. Retrying the claim in a loop was rejected as more code for a case that needs two requests within milliseconds.
- **Completion and release act only on `IN_PROGRESS` rows** (accepted assumption). A release can therefore never delete a `COMPLETED` key, and a completion after JOB-05 purged the claim updates nothing and logs the warning of the spec.
- **A replay whose order is missing answers `500`** (`IllegalStateException`). The spec does not mention it; orders are never deleted and a row becomes `COMPLETED` only in the transaction that stores its order, so this would be a bug, not a client error.
- **A replay's `reservationExpiresAt` has microsecond precision.** The first answer is built from the order in memory (nanoseconds from the clock), the replay from the stored row (PostgreSQL keeps microseconds), so the two can differ below a microsecond (seen in the Compose check: `…715495825Z` vs `…715496Z`). Same instant for any client purpose; truncating the clock in `OrderEntity.place` would change every first answer and was left alone.
- **Two existing tests changed beyond the controller mocks** (see the fix above): `SecurityConfigTest` (mock moved to the new method, assertions unchanged) and the `OrderPlaced` probe of `CheckoutIntegrationTest` (picks its own order's record instead of the first one). The probe change makes the test independent of the order the tests run in; filtering by key was preferred over waiting in every keyed test for the outbox to drain.
- **`Retry-After` documented on the `409`.** The task asks for a `409 Problem`; the header is documented too, as on every `503`, because the client should honour it.

*Spec sync (2026-10-22):* now part of the Order spec (EP-ORD-02, *Idempotency-Key*): the `409` when the row is gone at lookup, complete and release acting only on `IN_PROGRESS` rows, the `500` for a missing order and the precision of a replayed `reservationExpiresAt`. The test and class-structure deviations are implementation details and stay here only.
